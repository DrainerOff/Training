# ADR-001: Offline-first PWA + Google Apps Script как API синхронизации

**Статус:** принято · **Дата:** 2026-10-17

## Контекст

* Один пользователь, 4 тренировки в неделю, ввод в зале с iPhone, часто без связи.
* Обязательно: запуск без интернета после полного закрытия, продолжение тренировки, локальное сохранение каждого изменения, синхронизация без дубликатов, видимый статус.
* Хранилище должно остаться в Google Таблице: ChatGPT читает её через Google Drive.
* Нельзя: свой сервер, постоянный деплой, платная инфраструктура, порча существующей таблицы.

## Рассмотренные варианты

| Вариант | Офлайн-запуск | Обслуживание | Вывод |
|---|---|---|---|
| **A. Apps Script Web App (HtmlService) отдаёт интерфейс** | ✗ — страница в iframe на `*.googleusercontent.com`, Service Worker и манифест недоступны; без сети не открывается | минимальное | не выполняет обязательное требование |
| **B. Статическое PWA + Apps Script как JSON API** | ✓ — Service Worker кэширует приложение, данные в IndexedDB | статический хостинг бесплатно, деплой = `git push` | **выбран** |
| C. PWA + Google Sheets API напрямую (OAuth в браузере) | ✓ | нужен Google Cloud проект, экран согласия, токены живут час, OAuth-попапы ненадёжны в standalone-режиме iOS | сложнее и хрупче B |
| D. PWA + Firebase/Supabase | ✓ | отдельный сервис, данные не в таблице, нужен экспорт для ChatGPT | противоречит цели «данные в таблице» |

## Решение

```
app/ (статика на GitHub Pages: CI публикует ветку gh-pages после зелёных тестов)
  Service Worker ── precache всего приложения (версия = хэш коммита)
  IndexedDB      ── sessions, sets, metrics, kv, outbox
  Sync engine    ── POST text/plain JSON {action:'sync', token, since, push} ──► Apps Script /exec
                                                                                     │ LockService
                                                                                     ▼
                                                     Таблица: App_Sets / App_Sessions / App_Metrics / App_Program / App_Summary
```

### Модель данных

* **Сессия** (`App_Sessions`): `id, date, cycle, week (1–3), day, status (active|done), items[]`. `items` — снимок дня программы на момент старта; правки программы не переписывают историю. Каждый item: слот, категория, варианты, текущий вариант (`seriesKey`), отметки (боль / техника / новая точка отсчёта), заметка.
* **Подход** (`App_Sets`): одна строка = один подход с собственными `weight, reps, rir, drop, pain, technique`. `seriesKey` — силовая серия, то есть конкретный вариант упражнения. Дата, цикл, неделя, день продублированы для читаемости.
* **Метрики** (`App_Metrics`): одна запись на дату, `id = m<дата>` — детерминированный, поэтому дублей между устройствами не бывает.
* **Программа** (`App_Program`): строки «день — упражнение — альтернативы — категория — шаг — особые подходы — ключи серий». Колонка `keys` сохраняет связь истории при переименовании.

### Синхронизация и защита от дублей

1. Каждое изменение пишется в IndexedDB **одной транзакцией** вместе с записью в `outbox`, до любой сети.
2. Записи не удаляются физически: `deleted = true` тоже синхронизируется.
3. `updatedAt` у записи строго растёт при каждом изменении. Сервер делает upsert **по id** и применяет только более новую версию. Повтор того же запроса ничего не меняет, поэтому потерянный ответ безопасен.
4. Клиент убирает запись из outbox, только если её не меняли, пока шёл запрос.
5. Pull инкрементальный: сервер ставит строкам монотонный `_srv`, клиент хранит курсор. Ручные правки в листах получают новый `_srv` через `onEdit`.
6. Стартовая программа на новом устройстве имеет `updatedAt = 0` и не отправляется, поэтому не может затереть настоящую. Ручная правка `App_Program` определяется по хэшу и становится самой новой версией.
7. Двойное касание: в UI кнопка блокируется на время записи, в хранилище одинаковый подход в пределах 1,5 с считается тем же касанием.
8. Синхронизация запускается при старте, при появлении сети, при возврате в приложение, через 2,5 с после изменения и раз в минуту, пока есть очередь. Background Sync на iOS нет, поэтому данные уходят, когда приложение открыто, и статус это показывает.

### Безопасность

* Веб-приложение развёрнуто «от моего имени, доступ: все». Каждый запрос проверяется 64-символьным случайным ключом из Script Properties, сравнение — за постоянное время. Без ключа API ничего не читает и не пишет. Ключ меняется командой «Сменить ключ доступа», старый перестаёт работать сразу.
* Запросы больше 5 МБ отклоняются до разбора.
* ID таблицы берётся только из Script Properties (его сохраняет `setup`), а не из запроса. Поэтому API не может обратиться к другим файлам владельца.
* CSP страницы: скрипты только с собственного домена, сетевые запросы только к `script.google.com` / `*.googleusercontent.com`. Внедрённый код не сможет отправить ключ на посторонний хост.
* URL и ключ хранятся только на телефоне (IndexedDB), в коде и репозитории их нет.
* Пользовательский текст, начинающийся с `= + - @`, записывается как текст: формулы не исполняются.
* Скрипт пишет только в листы `App_*`. `describeLegacySheets` старые листы только читает.

### CORS

Apps Script не отвечает на preflight. Поэтому запросы — `POST` с `Content-Type: text/plain`, то есть «простой» CORS-запрос. Google отвечает редиректом на `script.googleusercontent.com`, где выставлен `Access-Control-Allow-Origin: *`. Этот путь воспроизведён в локальной эмуляции (`tests/helpers/servers.js`): эмулятор отклоняет preflight и не-`text/plain`.

### Запуск и обновления

Запуск никогда не ждёт бесконечно. Это следствие сбоя на реальном iPhone: в обычной вкладке Safari был вечный экран «Загрузка…», а в приватной всё работало.

* **Причина.** Старый `main.js` до появления интерфейса ждал IndexedDB (открытие → чтение → запись импорта) без ограничения по времени. В WebKit известны сбои, когда запрос к дисковой IndexedDB не отвечает ни успехом, ни ошибкой ([226547](https://bugs.webkit.org/show_bug.cgi?id=226547), [197050](https://bugs.webkit.org/show_bug.cgi?id=197050)). В приватной вкладке база живёт в памяти, поэтому там сбоя не было. Ошибку загрузки модуля тоже никто не ловил.
* **`boot.js`** — обычный (не модульный) скрипт, он выполняется раньше модулей. `main.js` сообщает ему этапы: `modules` → `storage-open` → `storage-read` → `storage-write` → `import` → `ui`. Если этап не закончился вовремя или модуль не загрузился, вместо «Загрузка…» появляется экран «Приложение не запустилось». На нём указан этап и есть кнопки «Повторить», «Скопировать отчёт», «Обновить файлы приложения». Ни экран, ни кнопки не трогают IndexedDB.
* **IndexedDB** (`db.js`): у каждого запроса есть срок. Открытие — 4 с, две попытки; перед каждой база «будится» вызовом `indexedDB.databases()` — обход ошибки Safari 14. Чтение — 15 с, запись — 8 с плюс 5 мс на запись, чтобы большая резервная копия не упиралась в срок. Зависшая транзакция записи отменяется, поэтому результат однозначен: подход либо сохранён вместе с очередью, либо не сохранён. Опоздавшее соединение закрывается.
* **Проверка записи при запуске.** До первого подхода приложение пишет в `kv.lastLaunchAt`. Так нерабочее хранилище видно сразу, а не посреди тренировки.
* **Временный режим** (только в памяти) включается только кнопкой «Продолжить без сохранения» на экране диагностики, рядом с предупреждением. Работает до закрытия вкладки, в приложении всё время висит красная плашка. Молча подменять постоянное хранилище временным приложение больше не может.
* **Перенос из таблицы** — отдельный этап после проверки записи, у его записи тот же срок. Ошибка не останавливает запуск: показывается сообщение, а при следующем запуске перенос повторяется.
* **Обновление Service Worker.** Новый выпуск скачивается целиком и ждёт. Управление он получает по сигналу `skip-waiting` от страницы, которая уже загрузила весь свой код, поэтому файлы двух выпусков на одной странице не смешиваются. Потом страница предлагает «Перезапустить». Исключение — выпуски без `boot.js` (ea0febc): их страница может зависнуть и сигнал не пришлёт, поэтому такой выпуск заменяется сразу.
* **`Cache-Control: no-cache` у копий в кэше SW.** GitHub Pages отдаёт файлы с `max-age=600`. С таким заголовком браузер до 10 минут берёт модуль из своей памяти, не спрашивая SW, и после обновления или восстановления в той же вкладке может выполниться старый файл. Это воспроизведено в тестах.
* **Самовосстановление.** Если модуль не загрузился, `boot.js` один раз сам просит SW скачать все файлы заново (`refresh-cache`, всё или ничего) и перезапускает страницу. Если SW не отвечает (старый или сломанный), его регистрация и кэш файлов удаляются, и следующий запуск идёт из сети. Без сети ничего не удаляется. Защита от циклов: не чаще раза в 2 минуты, иначе показывается экран диагностики.

Регрессионные тесты — `tests/e2e/update.spec.js`:

* обновление с опубликованного ea0febc (`tests/fixtures/releases/`) с сохранением данных и без повторного импорта;
* повторный запуск с существующей базой и холодный старт офлайн;
* испорченный кэш, постоянно сломанный файл, файл, который не приходит;
* IndexedDB, которая молчит.

Тайм-ауты `db.js` на имитации IndexedDB проверяет `tests/unit/db.test.js`.

### Перенос из старой таблицы

Программа и тренировка 16.10.2026 прочитаны из Google Таблицы один раз, через коннектор и только на чтение. Они встроены в приложение как снимок ячеек и конвертер с тестами. Импорт выполняется один раз на устройстве, записи получают фиксированные id и время, поэтому повтор не создаёт дублей. Подробно — [IMPORT.md](IMPORT.md).

## Последствия

* + Запуск и работа без сети, мгновенный отклик: UI не ждёт сеть.
* + Нулевая стоимость и обслуживание; данные остаются в вашей таблице.
* + Логика Apps Script проверяется тестами в Node: настоящий `Code.gs` на эмуляции Sheets.
* − Данные уходят в таблицу, только пока приложение открыто (ограничение iOS).
* − Установленное на экран «Домой» приложение и вкладка Safari имеют разные хранилища. Настраивать нужно приложение с иконки; при переносе на новый телефон данные подтягиваются из таблицы.
* − Квоты Apps Script (личный аккаунт: ~90 мин выполнения в сутки) с огромным запасом покрывают ~100 синхронизаций в день по 1–3 с.
