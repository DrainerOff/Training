# Как выходят обновления

Адрес приложения не меняется: **https://draineroff.github.io/Training/**. На него публикуется только ветка `main`.

## Схема

```
ветка (fix/…, feature/…, claude/…) ──PR──► CI: все тесты ──merge──► main ──► CI: тесты + публикация в gh-pages ──► iPhone
                                                                         └──► тег vX.Y.Z + GitHub Release (workflow «Release»)
```

* **PR** — workflow «Tests and publish» прогоняет unit-, серверные и сквозные тесты (эмуляция iPhone, авиарежим, обновление с прошлых выпусков, блокировщики контента). Ничего не публикует.
* **Merge в `main`** — те же тесты, затем `app/` уходит в ветку `gh-pages` с номером сборки = первые 7 знаков коммита. Через 1–2 минуты GitHub Pages отдаёт новую версию.
* **Телефон** скачивает её в фоне. Открытое приложение предлагает «Перезапустить», закрытое — берёт новую версию при следующем запуске. Номер сборки — внизу Настроек.

## Выпуск версии

Номер — `MAJOR.MINOR.PATCH`: v1.0.1 — исправления, v1.1.0 — новые возможности, v2.0.0 — несовместимые изменения данных.

1. В ветке с изменениями: поднять версию в `app/js/main.js` (`VERSION`) и `package.json`, добавить раздел `## vX.Y.Z — дата` в [CHANGELOG.md](../CHANGELOG.md).
2. PR в `main` → зелёный CI → merge.
3. Дождаться зелёного «Tests and publish» на `main`. Последний коммит ветки `gh-pages` должен называться `Publish <сборка> from main`.
4. Проверить на iPhone: в Настройках новая сборка; короткий прогон по [ACCEPTANCE.md](ACCEPTANCE.md) — то, что затрагивали изменения.
5. **Actions → Release → Run workflow → Branch: `main` → Version: `X.Y.Z` → Run workflow.** Workflow ставит тег `vX.Y.Z` на опубликованный коммит и создаёт GitHub Release с текстом из CHANGELOG. Он откажется, если версия в коде другая, нет раздела в CHANGELOG или Pages отдаёт не этот коммит.
   Вместо кнопки можно запушить тег: `git tag -a vX.Y.Z <коммит> -m vX.Y.Z && git push origin vX.Y.Z` — проверки те же.

## Правила, которые защищают данные

* **Только вперёд.** Сборки начиная с «Рекордов» (база на телефоне версии 2) не откатываются на более старые. Ошибку исправляет следующая версия, а не возврат старой.
* **Изменение базы на телефоне** (`DB_VERSION` в `app/js/data/db.js`) — только добавлением хранилищ, без удаления и переименования. Нужен сквозной тест обновления с последнего выпуска: тестовая копия выпуска в `tests/fixtures/releases/`, пример — `tests/e2e/release.spec.js`.
* **Изменение `apps-script/Code.gs`**: старая версия приложения должна работать с новым скриптом, новая — со старым (данные ждут на телефоне). Владелец обновляет скрипт сам: вставить код → **Управление развертываниями → ✎ → Новая версия**. Новое развертывание не создаётся, URL и ключ не меняются. В описании выпуска это пишется явно.
* **Имена файлов** не должны попадать под фильтры блокировщиков контента (проверяет `tests/unit/blockers.test.js`).

## Если что-то сломалось после выпуска

1. Номер сборки из Настроек, скриншот, что делали. На экране диагностики — «Скопировать отчёт».
2. Исправление в ветке `fix/…` → PR → merge → выпуск `vX.Y.(Z+1)` по шагам выше.
3. Данные на телефоне при этом не трогаются: ни очистка Safari, ни переустановка не нужны.

## Настройки репозитория (один раз, владелец)

* **Settings → Pages:** Deploy from a branch → `gh-pages` / root. Уже так; при переходе на `main` не менялось.
* **Settings → Branches → Add branch ruleset** (по желанию): для `main` — Require a pull request before merging и Require status checks to pass → `test`. Тогда в `main` не попадёт ничего без зелёных тестов.
